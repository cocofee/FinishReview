# 终点问题清单实施方案（过线卡片 + 芯片对账）

日期：2026-10-14。状态：实施基线，替换 2026-10-13 “连续录像判读”方案的主线。原方案中仍然有效的时间契约、证据定位和资源优先级并入本文第 5、9 节；连续播放和四态覆盖降为处理问题时的辅助回放工具。

本文结论来自定边、同心、贺兰山三场真实录像的离线回放。原型脚本、过线卡片和统计结果在 `D:\orca\count-lab\out\crossing_cards_20261013`。

## 1. 要解决的问题

按操作员实际耗时排序：

1. **逐人判读最费时间**：500 ms 胶卷里同一个人从远到近出现多次，每人都要找过线帧、对号码。定边 295 人用了约 98 分钟，中位每人 11.5 秒。
2. **一人两芯片 / 芯片有、人没有**：一人带两块芯片、备用或测试芯片、重复读数、不是有效完赛的读数。
3. **视频有、芯片没有**：漏读者没有成绩。

目标：操作员只处理系统列出的问题；有芯片、视频也对得上的选手自动通过，不要求逐人确认，也不要求把整场录像按 1 倍速看完。

约束不变：

- 正式成绩以 CycleRace 芯片时间为准。视频只用于发现问题，以及为漏读者提供补录时间。
- 软件要分发给其他人，不使用 AGPL 组件。
- 现场笔记本同时运行 CycleRace，分析不能影响计时。保住 CycleRace 优先于一切分析功能。
- 比赛电脑只有核显：本机只在 CPU 上运行小模型（YOLOX 认车，只看候选截图）；大模型不在本机运行，只通过 API 调用。
- 判定顺序：本机先处理；本机定不了或有争议的，交人决定。大模型辅助暂缓（第 10 节）。
- 多圈赛只判最后一圈。

## 2. 方案总览

```text
芯片记录（CycleRace）                       录像（机位 1 / 2）
        │                                         │
  芯片自检（重复、测试/备用、过早、圈数、          沿终点线逐帧取一条像素
  应到未到、两边同步）                             → 过线事件（每次过线一个）
        │                                         │
        └──────────── 自动校时 + 漂移 ─────────────┘
                              │
                     按时间顺序一对一配对
                              │
          配上的：自动通过（单独记录，不冒充人工确认）
          配不上的：认车（YOLOX，本机）→ 合并规则
                              │
                   问题清单 + 过线卡片 + 集团核对
                              │
              操作员处理 → 导出补录 / 删除 / 改号清单 → CycleRace
```

核心变化：

- **按过线组织画面，不按时间采样**：每次过线生成一张“过线卡片”，即前轮压线那一刻的截图，并按时间挂上芯片号码。每个人只出现一次。
- **视频负责数人，不负责认人**：数过线不依赖号码牌。下午逆光、号码牌看不清时照样可用；只有处理问题时才需要看号码。
- **只把对不上的交给人**。

## 3. 三场回放结论

| 项目 | 定边（山地） | 同心（山地） | 贺兰山（公路，侧后方机位 2） |
| --- | --- | --- | --- |
| 有录像的芯片 | 298 | 415 | 294（10:32–11:16） |
| 校时 | 自动；人工首人校时只在开头准 | 自动；现场没有校时 | 自动；现场人工校时差了约 58 秒 |
| 时钟漂移 | −334 ms/小时 | −530 ms/小时 | −889 ms/小时 |
| 扣除漂移后的残差中位数 | 27 ms | 29 ms | 27 ms |
| 自动配对 | 270（91%） | 389（94%） | 242（82%） |
| 自行车识别（已配对骑手，YOLOX-S） | 99.3% | 98.6% | 95.2% |
| 问题清单 | 28 条 | 50 条（加车辆、阴影过滤后约 30 条） | 65 条（51 条是集团） |
| 已知漏读 | 307 已检出 | 642 已检出（现场未发现） | 319、550 未检出（都在大集团中） |
| 一人两芯片 / 无效读数 | 020/023、371/376 已检出 | 223/236、780 两条已检出 | — |

要点：

- **山地赛效果稳定**：九成以上芯片自动配对，人工只看几十条。定边与人工确认对照，96% 是同一次过线；回放还发现了 2 处人工确认错误：067 确认到 057 身上，051 确认到 029 身上。
- **公路赛**：
  - 单独过线的 78 组，视频人数与芯片数全部一致；2–3 人小组有 74% 一致。
  - 4 人以上的集团人数普遍偏少，10 人以上的 6 个集团全部不一致。
  - 并排相差 20–30 ms 的骑手被合并成一次过线，所以集团里的漏读不能只靠自动计数，需要第 7 节的集团核对。
- **自动校时是必需的**：
  - 三场漂移都在每小时 0.3–0.9 秒。
  - 人工校时只在锚点附近准，贺兰山机位 2 的人工校时还错了 58 秒。
- **现场环境会产生大量误报**：
  - 定边终点线上站人累计约 25 分钟；
  - 同心下午的长影子把一个人拆成两次过线；
  - 比赛结束后有车辆通过终点。

  这些都能用规则和车辆识别排除，但要靠现场纪律从源头减少。

## 4. 机位与画线（现场要求）

- **画线**：每个机位在软件中画一条终点线。优先画地面上清晰的线或白带；同心可沿用 `long_image_lines.json`。画线保存版本，改线后重新校时。
- **机位**：
  - 靠近终点线延长线，线在画面里要足够长；
  - 骑手过线后不要立刻出画（同心的线太靠画面边缘，认车时需要往前看 0.2–0.4 秒）。
  - 公路赛建议在龙门上增加一个垂直向下的机位，让并排的人在画面中自然分开。角度比像素更重要。
- **现场纪律**：
  - 比赛期间终点线前后不站人、不停车，工作人员不在线上逗留；
  - 测试芯片和回收的芯片盒不得经过天线；
  - 比赛结束前车辆不过线。

## 5. 时间模型

沿用原方案的时间契约：

- 芯片时间、录像时间、显示时间分开；
- 偏移只换算一次；
- 证据定位到稳定的源录像位置（会话、文件、帧、片内位置、校时版本）。

新增要求：

1. **自动粗校**：录像开始后，把过线时间与芯片时间做差，在 ±90 秒范围内按 100 ms 分箱，取峰值。三场都得到单一而明显的峰。
2. **自动细校和漂移**：只用前后 5 秒内没有别人的单独过线者，稳健拟合“偏移 = a + b × 时间”，剔除离群点。两段录像会话共用同一台电脑的时钟时，沿用同一条漂移线。
3. **人工校时只作为核对**：自动结果和人工锚点相差超过 300 ms 时，提示核对，不静默覆盖。
4. **校时版本**：每次重新拟合生成新版本；已处理的问题保留当时的版本。

## 6. 过线检测与配对

参数是三场回放用的初值，必须继续用真实录像验收，不作为保证。

| 步骤 | 做法 |
| --- | --- |
| 线取样 | 每帧沿终点线取 500 个点、4 像素宽，按时间拼成过线图；不用模型，CPU 占用见第 9 节 |
| 背景 | 每个位置取前后约 6 秒的中位数作为背景，并扣除整体亮度变化 |
| 过线事件 | 与背景的颜色差超过阈值的连通区域；同一人的碎片按“起点相近或仍在原位置”合并 |
| 像骑手 | 线上遮挡高度至少约 4%、持续不超过 1 秒；更长的遮挡记为“线被挡”时段 |
| 被挡时段 | 线上站人时，在遮挡内找短促的剧烈变化，只用于给芯片配对，不单独报“无芯片” |
| 配对 | 按时间顺序一对一对齐，容差 ±0.7 秒；单独过线者放宽到 ±1.5 秒（同心 744 的芯片比过线晚 1.4 秒） |

录像定位必须精确：

- 贺兰山机位 2 是 H.265，按时间跳转会晚约 1.8 秒，文件头的帧率也不对。
- 取帧一律先跳到目标前 4 秒，再顺序读到目标帧。
- 卡片和精判都只用实际解码出来的帧时间。

## 7. 问题清单

### 7.1 认车（只对配不上的过线）

- 本机用 YOLOX-S（Apache-2.0），单线程、低优先级运行。只对候选过线取 1–3 帧截图检测，不逐帧运行。认车不依赖网络。
- 侧拍机位要看压线前 0.2–0.4 秒，那时整辆车还在画面里。
- 类别：自行车、行人、摩托车、汽车、卡车。
  - 有自行车压在线上的，保留；
  - 只有行人或车辆、且把握高的，移到清单末尾的“已排除”，可展开查看，不删除。
- 以下情况不自动排除，标为“有争议”，留在清单里由人决定：
  - 把握不高，或几帧的结论不一致；
  - 截图里的人被画面边缘切掉；
  - 发生在终点线拥挤的时段。拥挤时被挡住的骑手容易被认成行人，定边的 034、337 都是这种情况。
- 拥挤时段本身整段列为“现场拥挤，证据不足”，由人核对。

### 7.2 合并规则

- 芯片预期时间 0.8 秒以内的多余过线，算同一个人（同心下午影子造成 147 次重复）。
- 同一位置 90 秒内反复出现的活动，合并成一条“有人停留”。
- 迟到的芯片在放宽窗口内与单独过线配对。

注意：第一条规则会掩盖紧跟在别人后面的无芯片骑手，所以 4 人以上的集团一律另做第 7.4 节的集团核对。

### 7.3 清单类型

| 类型 | 来源 | 操作员选择 |
| --- | --- | --- |
| 有人过线，没有芯片 | 配不上芯片的骑车过线 | 认号补录 / 非选手 / 往回骑或推车 |
| 一次过线，两个芯片 | 两个芯片对应同一次过线 | 删除多余芯片 / 确认是并排两人 |
| 有芯片，没看到过线 | 芯片附近没有过线 | 看录像 / 删除芯片 / 证据不足 |
| 集团核对 | 4 人以上、相隔 2 秒以内的集团 | 见第 7.4 节 |
| 线被挡 / 拥挤时段 | 长时间遮挡 | 人工核对该时段 |
| 录像缺口内的芯片 | 没有录像覆盖 | 标记无法核实，不算通过 |

只用芯片数据的检查，不需要视频，比赛中实时就能出结果：

- 同号或同芯片几秒内重复读数，包括重复补录（贺兰山 550 有两条有效的补录）；
- 测试组、备用组或名单外的芯片，以及 1 秒内成批读数；
- 发枪后不可能这么早到达的读数（贺兰山 746 开赛 11 分钟就有读数），需要 CycleRace 提供各组发枪时间；
- 多圈赛的圈数异常：圈号重复或倒退、单圈用时异常、末圈缺读；
- 应到未到：名单减去已到和退赛（需要 CycleRace 提供退赛、OTL 状态）；
- 两边同步检查：CycleRace 的补录、作废和 FinishReview 收到的不一致时提示。贺兰山的 319 补录、701 作废都没有同步过来。

### 7.4 集团核对（公路赛必需）

- 系统自动找出集团，生成一条核对项，包含：
  - 过线图；
  - 可逐帧拖动的慢放画面，最好用俯拍或终点摄影角度的机位；
  - 芯片名单和数量。
- 操作员在过线图或慢放画面上逐个点击骑手，系统统计人数，并和芯片数对比：
  - 人数多于芯片：找出多出的人（看号码牌，或用“应到未到”名单排除），然后补录；
  - 人数少于芯片：检查一人两芯片或无效读数。
- 点击时同时记录每人的过线帧。补录时间按视频中前后两人的芯片时间插值，不单纯用偏移换算，避免集团内名次错乱。
- 过线图上标出每个芯片的预期过线时刻。点数时，系统把点击和芯片按时间对齐，提示多出的人可能在哪个位置。
- 贺兰山 6 个 10 人以上的集团加 11 个 4–9 人的集团，预计 10 分钟左右能核完，待原型实测。

## 8. 界面与交接

- **主入口是问题清单**：
  - 顶部汇总“自动通过 N 人、待处理 M 条、无法核实 K 人”。
  - 每条显示卡片、时间、相关号码和可选处理；点击后跳到原帧，附前后各约 1 秒的小胶卷。
  - 原有逐帧精判、放大和标线功能保留，用于处理单条问题。
- **防呆**：同一帧、同一位置确认第二个号码时必须提示。定边 029/051 就是这样确认错的。
- **处理记录**：每次处理都记录原因、证据帧和校时版本。
  - 本地“删除记录”改为带原因的标记，绑定号码、芯片和时间，上游一改就重新提示；
  - 不能只按记录编号永久隐藏，因为 CycleRace 会复用编号。
- **导出给 CycleRace 三张清单**：
  - 补录：号码、芯片域时间、证据帧；
  - 建议删除；
  - 建议改号或改圈。

  CycleRace 改完后，FinishReview 收到修订就自动关闭对应问题。

## 9. 资源与性能（保住 CycleRace）

原则：FinishReview 的分析可以暂停、可以晚出结果、可以关闭；CycleRace 计时不能受任何影响。

- **优先级**：CycleRace 计时 > 录像写盘 > 当前处理的画面 > 线取样 > 认车 > 其他。
- **本机做三件事**：录像写盘（已有）、线取样和认车。
  - 线取样只是解码录像、沿线取一条像素，不运行模型；
  - 认车用 YOLOX，只看候选截图。
- **线取样实测**（与比赛电脑同型号的 i5-13500H 笔记本，2026-10-14，每个机位限 2 个解码线程）：

  | 录像 | 保持实时所需 CPU | 最快速度 | 内存峰值 |
  | --- | --- | --- | --- |
  | 定边 2560×1920 H.264，20 帧/秒 | 0.54 核 | 67 帧/秒 | 139 MB |
  | 贺兰山机位 2 2560×1440 H.265，25 帧/秒 | 0.46 核 | 97 帧/秒 | 119 MB |
  | 贺兰山机位 1 1920×1080，25 帧/秒 | 0.20 核 | 192 帧/秒 | 88 MB |

  两个机位合计约 0.7–1.1 个核，约占 16 个线程的 4–7%。通过 OpenCV 用核显硬件解码反而更耗 CPU（定边 0.79 核），因为画面要拷回内存再转换颜色，所以不采用。
- **认车实测**（同一台电脑）：
  - YOLOX-S 按 OpenCV 默认设置，每张 0.22 秒，但运行的瞬间占满约 10 个核，不能这样用；
  - 限成单线程后，每张约 1.5 秒，只占 1 个核，内存约 300 MB；
  - 每场几百张截图，合计占单核几分钟到二十分钟，分散在整场；
  - CPU 紧张时可换 YOLOX-nano：单线程每张 0.07 秒、79 MB，但定边的自行车识别率从 99.3% 降到 97.8%。
- **限制**：
  - 分析进程以低优先级运行，并开启 Windows 效率模式，让系统尽量把它放在能效核上；
  - 每个机位最多 2 个解码线程；YOLOX 单线程，同一时间只运行一个；
  - 过线图分段写盘，不在内存里累积整场；
  - CPU 总占用持续偏高时暂停取样和认车，空闲后补算。分析落后只会让清单晚出，不影响录像和计时。
- **不碰 CycleRace 的数据库**：比赛中只通过现有事件接口接收芯片记录，不直接打开 CycleRace 的 `race.db`，避免读操作和计时写入争锁。赛后分析用副本。
- **离线版**：整场录像分析在比赛结束后运行，或在另一台电脑上运行，按时长和分辨率需要 10–40 分钟。

## 10. DeepSeek 辅助（暂缓）

> 2026-10-14 决定先不考虑。主流程不依赖本节，有争议的条目直接由人处理。本节保留调研结论和测试设计，以后需要时再评估。

设想中，DeepSeek 只通过 API 使用，放在本机流程的最后、人工之前：

```text
本机处理（过线图、配对、YOLOX、规则）→ 有争议的条目交 DeepSeek → 意见和理由 → 人最终决定
```

- **只看有争议的**：配上芯片的、本机有把握排除的，不发给 DeepSeek。每场预计几十到一两百条。
- **帮着数人，不认号码**：号码牌常被挡住，公路车和山地车也会混在一起过线。DeepSeek 只回答“几个人”“是不是骑车冲线”“什么车型”，不读号码。
- **只给意见，不做决定**：意见和理由显示在条目上，并预选处理选项；最终由人确认。DeepSeek 不改成绩，也不自动结案。

**能力与费用**（2026-10-14 查官方文档）：

- **模型**：`deepseek-flash`（V4.1-Flash，2026-09-10 发布）能看图片；`deepseek-v4-pro` 只能处理文字。
- **图片**：大于约 1300×1300 像素会被缩小，每张最多 1024 个 token；小于约 544×544 的会被放大。所以只发终点线附近 600–1000 像素的局部截图，不发整帧。
- **价格**：每百万 token 输入 0.15–0.3 美元，输出 0.6–1.2 美元。工作日北京时间 9–12 点、14–18 点按高峰价，其余时间和周末半价。按每场 300 次请求估算，每场不到 1 美元，待实测。
- **分发**：调用 API 不需要随软件分发模型，不涉及 AGPL。软件不内置 API Key，由使用者自己配置。

**哪些条目交给 DeepSeek**：

| 有争议的条目 | 发送内容 | DeepSeek 回答 | 给人的帮助 |
| --- | --- | --- | --- |
| 有人过线，没有芯片（含第 7.1 节认车有争议的） | 压线前、压线时各 1 张截图 | 骑车冲线 / 行人或工作人员 / 车辆 / 影子 / 往回骑或推车；车型：公路车 / 山地车 | 预选“认号补录”或“非选手”；公路、山地一起过线时，把“应到未到”候选缩小到对应组别 |
| 一次过线，两个芯片 | 两个机位压线时的截图 | 1 人 / 2 人 / 看不清 | 预选“删除多余芯片”或“并排两人” |
| 有芯片，没看到过线 | 芯片时间前后的截图 | 有没有骑手过线 | 预选“看录像”或“建议删除” |
| 集团人数对不上 | 按芯片时间把集团切成每段 2–4 人，每段每个机位 1 张截图 | 每段人数 | 指出多出的人可能在哪一段，集团核对从这段开始；不能代替点数 |
| 对账、应到未到、两边记录不一致 | 只发文字：分组别、分圈的芯片数，视频计数，应到未到，补录和作废记录 | 一句话结论、候选号码、建议操作 | 显示在问题旁边；起草补录、删除、改号清单和赛后报告；回答操作员提问 |

对账的回答示例：“这团芯片 19 个，点数 20 人，多 1 人。应到未到里同组别的有 3 人；分段数人显示第 3 段多 1 人，建议先看第 3 段。”

候选号码由程序按名单、组别、圈数和速度算出，DeepSeek 只负责排序和说明。回答里出现名单外的号码，直接丢弃。

**保住 CycleRace 的规则**：

- **请求**：在后台排队，一次一个，超时 30 秒，最多重试 1 次。任何失败都不影响清单、画面和计时。
- **上传**：
  - 只发待处理问题的局部截图，JPEG 每张约 100 KB；
  - 上传限速，例如 100 KB/秒；
  - 集团冲线、芯片读数密集时暂停发送，过后再补发；
  - 估计每场上传 50–100 MB。
- **隐私**：文字里只有号码、组别、时间和人数，不发姓名、证件号、电话。选手图片发到云端需要主办方同意。
- **没网或没配 API Key**：本机认车和问题清单照常；有争议的条目没有 DeepSeek 意见，直接由人处理。
- **记录**：每次请求记录模型名、发送内容、回答和费用，便于事后追查。

**启用前先用三场已知答案测**：

| 条目 | 已知答案 |
| --- | --- |
| 有人过线，没有芯片 | 三场清单里的行人、头盔、车辆、影子、推车往回走的人；307、642 两个真实漏读必须判为骑车冲线 |
| 车型 | 已配对的骑手：贺兰山是公路赛，定边、同心是山地赛 |
| 一次过线，两个芯片 | 定边 14 组并排两人；020/023、371/376 和同心 223/236 是一人 |
| 有芯片，没看到过线 | 同心 780 两条应判无人；定边过线检测漏掉的 2 条应判有人，被人挡住镜头的 3 条应判看不清 |
| 集团人数对不上 | 贺兰山 10:58 那团 20 人（含漏读的 319）、11:03 那团 13 人（含 550），看能否指出多出的人所在的段 |
| 对账 | 贺兰山 319 补录未同步、550 重复补录、701 作废未同步；同心 642 整场未读 |

- **测试方法**：同时比较思考模式开、关两种设置的准确率、耗时和费用。
- **启用标准**：对真实漏读者不能给出“不是选手”的意见；各类条目准确率达标才显示意见，不达标的不显示。

## 11. 实施步骤与验收

| 步骤 | 交付 | 验收 |
| --- | --- | --- |
| 1 时间与同步 | 原方案的时间契约；自动粗校、细校和漂移；CycleRace 同步检查 | 三场自动偏移与人工锚点一致（贺兰山机位 2 能指出人工校时错误）；残差中位数 ≤ 50 ms |
| 2 芯片自检清单 | 7.3 节中只用芯片数据的检查 | 能列出三场已知的测试芯片、重复补录、过早读数、未同步记录 |
| 3 离线问题清单 | 读归档录像：线取样、过线、配对、认车（YOLOX，单线程）、规则、卡片 | 三场已知问题全部检出（307、020/023、371/376、223/236、780、642）；山地赛清单 ≤ 有录像人数的 15%；注入测试（删或加芯片读数）能检出 |
| 4 卡片界面与交接 | 问题清单界面、处理按钮、防呆、三张导出清单 | 用定边录像实测处理时间，对比原来的 98 分钟 |
| 5 集团核对 | 过线图、慢放、点击计数、插值补录时间 | 贺兰山 319、550 能在集团核对中找出；记录每个集团的耗时 |
| 6 赛中实时 | 边录边取样、分批出清单，资源按第 9 节限制 | 与 CycleRace 同机连续运行一整场（可回放芯片数据模拟）：CycleRace 收到的读数不延迟、不丢失；实测取样 CPU、内存和清单延迟 |
| 7 可选：俯拍机位 | 公路赛加一个垂直向下的机位 | 用公路赛实测后决定 |

每一步都单独修改、单独验收，完成后再进入下一步。规则和阈值只在三场比赛上调过，第四场比赛用于盲测。

## 12. 与原方案的关系

- **保留**：
  - 三种时间分开、偏移只换算一次、证据定位到原帧；
  - 不按最近芯片自动认人；
  - 现场录像优先；
  - 新芯片不抢占当前画面。
- **降级**：
  - 连续延迟回放、四态覆盖和自动倍率，只作为处理问题时的回放工具；
  - 不再要求把整场录像按 1 倍速看完才算“已判读”。
- **移除**：用“全程覆盖率”衡量判读完成度。改为两项：问题清单是否处理完，以及录像和证据缺口是否如实列出。
- **保留文档**：`CONTINUOUS_REVIEW_DESIGN.md` 保留交互与前后台隔离背景；`docs/LIVE_COUNT_REVIEW_PLAN.md` 的外部计数与“疑似额外芯片”等状态定义并入本文第 7 节。

## 13. 已知限制

- **公路密集集团**：自动计数不可靠，依赖集团核对和机位改进。
- **证据不足**：拥挤、遮挡、录像缺口只能如实报告，不能补出证据。
- **号码牌**：常被挡住或看不清，系统不识别号码。数人数不需要号码；漏读者的身份由人确认：先用“应到未到”名单排除，再看卡片上的车型和衣着缩小范围。
- **验证范围**：参数来自三场比赛，规模和场地类型有限。
