# 终点问题清单实施方案（过线卡片 + 芯片对账）

日期：2026-10-14。状态：实施基线，替换 2026-10-13 “连续录像判读”方案的主线。原方案中仍然有效的时间契约、证据定位和资源优先级并入本文第 5、9 节；连续播放和四态覆盖降为处理问题时的辅助回放工具。

本文结论来自定边、同心、贺兰山三场真实录像的离线回放。原型脚本、过线卡片和统计结果在 `D:\orca\count-lab\out\crossing_cards_20261013`。

## 1. 要解决的问题

按操作员实际耗时排序：

1. **逐人判读最费时间**：500 ms 胶卷里同一个人从远到近出现多次，每人都要找过线帧、对号码。定边 295 人用了约 98 分钟，中位每人 11.5 秒。
2. **一人两芯片 / 芯片有、人没有**：一人带两块芯片、备用或测试芯片、重复读数、不是有效完赛的读数。
3. **视频有、芯片没有**：漏读者没有成绩。

目标：操作员只处理系统列出的问题；有芯片、视频也对得上的选手自动通过，不要求逐人确认，也不要求把整场录像按 1 倍速看完。

约束不变：

- 正式成绩以 CycleRace 芯片时间为准。视频只用于发现问题，以及为漏读者提供补录时间。
- 软件要分发给其他人，不使用 AGPL 组件。
- 现场笔记本同时运行 CycleRace，分析不能影响计时。
- 多圈赛只判最后一圈。

## 2. 方案总览

```text
芯片记录（CycleRace）                       录像（机位 1 / 2）
        │                                         │
  芯片自检（重复、测试/备用、过早、圈数、          沿终点线逐帧取一条像素
  应到未到、两边同步）                             → 过线事件（每次过线一个）
        │                                         │
        └──────────── 自动校时 + 漂移 ─────────────┘
                              │
                     按时间顺序一对一配对
                              │
          配上的：自动通过（单独记录，不冒充人工确认）
          配不上的：认车（自行车 / 行人 / 车辆）→ 合并规则
                              │
                   问题清单 + 过线卡片 + 集团核对
                              │
              操作员处理 → 导出补录 / 删除 / 改号清单 → CycleRace
```

核心变化：

- **按过线组织画面，不按时间采样**：每次过线生成一张“过线卡片”，即前轮压线那一刻的截图，并按时间挂上芯片号码。每个人只出现一次。
- **视频负责数人，不负责认人**：数过线不依赖号码牌。下午逆光、号码牌看不清时照样可用；只有处理问题时才需要看号码。
- **只把对不上的交给人**。

要点：

- **山地赛效果稳定**：九成以上芯片自动配对，人工只看几十条。定边与人工确认对照，96% 是同一次过线；回放还发现了 2 处人工确认错误：067 确认到 057 身上，051 确认到 029 身上。
- **公路赛**：
  - 单独过线的 78 组，视频人数与芯片数全部一致；2–3 人小组有 74% 一致。
  - 4 人以上的集团人数普遍偏少，10 人以上的 6 个集团全部不一致。
  - 并排相差 20–30 ms 的骑手被合并成一次过线，所以集团里的漏读不能只靠自动计数，需要第 7 节的集团核对。
- **自动校时是必需的**：
  - 三场漂移都在每小时 0.3–0.9 秒。
  - 人工校时只在锚点附近准，贺兰山机位 2 的人工校时还错了 58 秒。
- **现场环境会产生大量误报**：
  - 定边终点线上站人累计约 25 分钟；
  - 同心下午的长影子把一个人拆成两次过线；
  - 比赛结束后有车辆通过终点。

  这些都能用规则和车辆识别排除，但要靠现场纪律从源头减少。

## 4. 机位与画线（现场要求）

- **画线**：每个机位在软件中画一条终点线。优先画地面上清晰的线或白带；同心可沿用 `long_image_lines.json`。画线保存版本，改线后重新校时。
- **机位**：
  - 靠近终点线延长线，线在画面里要足够长；
  - 骑手过线后不要立刻出画（同心的线太靠画面边缘，认车时需要往前看 0.2–0.4 秒）。
  - 公路赛建议在龙门上增加一个垂直向下的机位，让并排的人在画面中自然分开。角度比像素更重要。
- **现场纪律**：
  - 比赛期间终点线前后不站人、不停车，工作人员不在线上逗留；
  - 测试芯片和回收的芯片盒不得经过天线；
  - 比赛结束前车辆不过线。

## 5. 时间模型

沿用原方案的时间契约：

- 芯片时间、录像时间、显示时间分开；
- 偏移只换算一次；
- 证据定位到稳定的源录像位置（会话、文件、帧、片内位置、校时版本）。

新增要求：

1. **自动粗校**：录像开始后，把过线时间与芯片时间做差，在 ±90 秒范围内按 100 ms 分箱，取峰值。三场都得到单一而明显的峰。
2. **自动细校和漂移**：只用前后 5 秒内没有别人的单独过线者，稳健拟合“偏移 = a + b × 时间”，剔除离群点。两段录像会话共用同一台电脑的时钟时，沿用同一条漂移线。
3. **人工校时只作为核对**：自动结果和人工锚点相差超过 300 ms 时，提示核对，不静默覆盖。
4. **校时版本**：每次重新拟合生成新版本；已处理的问题保留当时的版本。

## 6. 过线检测与配对

参数是三场回放用的初值，必须继续用真实录像验收，不作为保证。


| 步骤   | 做法                                                                |
| ---- | ----------------------------------------------------------------- |
| 线取样  | 每帧沿终点线取 500 个点、4 像素宽，按时间拼成过线图；单路解码约 21–28 帧/秒，满足 20–25 帧/秒录像的实时要求 |
| 背景   | 每个位置取前后约 6 秒的中位数作为背景，并扣除整体亮度变化                                    |
| 过线事件 | 与背景的颜色差超过阈值的连通区域；同一人的碎片按“起点相近或仍在原位置”合并                            |
| 像骑手  | 线上遮挡高度至少约 4%、持续不超过 1 秒；更长的遮挡记为“线被挡”时段                             |
|      | 线上站人时，在遮挡内找短促的剧烈变化，只用于给芯片配对，不单独报“无芯片”                             |
|      | 按时间顺序一对一对齐，容差 ±0.7 秒；单独过线者放宽到 ±1.5 秒（同心 744 的芯片比过线晚 1.4 秒）        |


录像定位必须精确：

- 贺兰山机位 2 是 H.265，按时间跳转会晚约 1.8 秒，文件头的帧率也不对。
- 取帧一律先跳到目标前 4 秒，再顺序读到目标帧。
- 卡片和精判都只用实际解码出来的帧时间。

## 7. 问题清单

### 7.1 认车（只对配不上的过线）

- 用 YOLOX-S（Apache-2.0）。只对候选过线取 1–3 帧截图检测，不逐帧运行。
- 侧拍机位要看压线前 0.2–0.4 秒，那时整辆车还在画面里。
- 类别：自行车、行人、摩托车、汽车、卡车。
  - 有自行车压在线上的，保留；
  - 只有行人或车辆的，自动排除，并在清单末尾留可展开的记录。
- 终点线拥挤的时段不自动排除，整段列为“现场拥挤，证据不足”。拥挤时被挡住的骑手容易被认成行人：定边的 034、337 都是这种情况。

### 7.2 合并规则

- 芯片预期时间 0.8 秒以内的多余过线，算同一个人（同心下午影子造成 147 次重复）。
- 同一位置 90 秒内反复出现的活动，合并成一条“有人停留”。
- 迟到的芯片在放宽窗口内与单独过线配对。

注意：第一条规则会掩盖紧跟在别人后面的无芯片骑手，所以 4 人以上的集团一律另做第 7.4 节的集团核对。

### 7.3 清单类型


| 类型         | 来源                | 操作员选择               |                  |
| ---------- | ----------------- | ------------------- | ---------------- |
| 有人过线，没有芯片  | 配不上芯片的骑车过线        | 认号补录 / 非选手 / 往回骑或推车 |                  |
| 被挡时段       |                   |                     |                  |
| 配对         | 一次过线，两个芯片         | 两个芯片对应同一次过线         | 删除多余芯片 / 确认是并排两人 |
| 有芯片，没看到过线  | 芯片附近没有过线          | 看录像 / 删除芯片 / 证据不足   |                  |
| 集团核对       | 4 人以上、相隔 2 秒以内的集团 | 见第 7.4 节            |                  |
| 线被挡 / 拥挤时段 | 长时间遮挡             | 人工核对该时段             |                  |
| 录像缺口内的芯片   | 没有录像覆盖            | 标记无法核实，不算通过         |                  |


只用芯片数据的检查，不需要视频，比赛中实时就能出结果：

- 同号或同芯片几秒内重复读数，包括重复补录（贺兰山 550 有两条有效的补录）；
- 测试组、备用组或名单外的芯片，以及 1 秒内成批读数；
- 发枪后不可能这么早到达的读数（贺兰山 746 开赛 11 分钟就有读数），需要 CycleRace 提供各组发枪时间；
- 多圈赛的圈数异常：圈号重复或倒退、单圈用时异常、末圈缺读；
- 应到未到：名单减去已到和退赛（需要 CycleRace 提供退赛、OTL 状态）；
- 两边同步检查：CycleRace 的补录、作废和 FinishReview 收到的不一致时提示。贺兰山的 319 补录、701 作废都没有同步过来。

### 7.4 集团核对（公路赛必需）

- 系统自动找出集团，生成一条核对项，包含：
  - 过线图；
  - 可逐帧拖动的慢放画面，最好用俯拍或终点摄影角度的机位；
  - 芯片名单和数量。
- 操作员在过线图或慢放画面上逐个点击骑手，系统统计人数，并和芯片数对比：
  - 人数多于芯片：找出多出的人（看号码牌，或用“应到未到”名单排除），然后补录；
  - 人数少于芯片：检查一人两芯片或无效读数。
- 点击时同时记录每人的过线帧。补录时间按视频中前后两人的芯片时间插值，不单纯用偏移换算，避免集团内名次错乱。
- 贺兰山 6 个 10 人以上的集团加 11 个 4–9 人的集团，预计 10 分钟左右能核完，待原型实测。

## 8. 界面与交接

- **主入口是问题清单**：
  - 顶部汇总“自动通过 N 人、待处理 M 条、无法核实 K 人”。
  - 每条显示卡片、时间、相关号码和可选处理；点击后跳到原帧，附前后各约 1 秒的小胶卷。
  - 原有逐帧精判、放大和标线功能保留，用于处理单条问题。
- **防呆**：同一帧、同一位置确认第二个号码时必须提示。定边 029/051 就是这样确认错的。
- **处理记录**：每次处理都记录原因、证据帧和校时版本。
  - 本地“删除记录”改为带原因的标记，绑定号码、芯片和时间，上游一改就重新提示；
  - 不能只按记录编号永久隐藏，因为 CycleRace 会复用编号。
- **导出给 CycleRace 三张清单**：
  - 补录：号码、芯片域时间、证据帧；
  - 建议删除；
  - 建议改号或改圈。

  CycleRace 改完后，FinishReview 收到修订就自动关闭对应问题。

## 9. 资源与性能

- **优先级**：CycleRace 计时 &gt; 录像写盘 &gt; 当前处理的画面 &gt; 线取样 &gt; 认车 &gt; 其他。分析进程低优先级运行，并限制线程数。
- **取样**：每个机位一路解码，实测 21–28 帧/秒（5 MP H.264）、约 25–50 帧/秒（2560×1440 H.265）。
- **YOLOX-S**：单张截图推理约 0.4 秒，单进程约 2 GB 内存。16 GB 的电脑最多同时跑两路；同时跑五路会内存不足。
- **离线版**：整场录像分析在 10–40 分钟内完成，取决于时长和分辨率。实时版要求处理延迟在几秒以内，待实测。

## 10. 大模型（如 DeepSeek）的定位

可以作为可选的辅助模块，但不进入计时和判定主流程。


| 适合                                | 不适合                |
| --------------------------------- | ------------------ |
| 读号码牌给建议：只在“应到未到”名单里选，输出候选和截图，由人确认 | 数集团人数（大模型对密集计数不可靠） |
| 把问题清单和处理记录整理成赛后报告、仲裁说明            | 决定过线时间、名次或自动补录     |
| 操作员用自然语言查询，比如“10:58 那团有哪些人”       | 逐帧实时分析             |


使用前提：

- **离线可用**：
  - 现场网络不稳定；
  - 选手图像发给云端服务涉及隐私，需征得同意；
  - 本机没有独立显卡，只能运行小模型，速度要实测。
- **先做对比测试**：用三场卡片上能看清的号码牌，比较大模型和专用 OCR（如 Apache-2.0 的 PaddleOCR）的识别准确率，达到要求才接入。
- **许可证逐个核对**：分发前确认所用模型的许可证。
- **只给建议**：所有输出都要人工确认，并记录模型版本。

号码牌看不清时，任何模型都读不出来。机位角度、光线和号码牌位置比模型更重要。

## 12. 与原方案的关系

- **保留**：
  - 三种时间分开、偏移只换算一次、证据定位到原帧；
  - 不按最近芯片自动认人；
  - 现场录像优先；
  - 新芯片不抢占当前画面。
- **降级**：
  - 连续延迟回放、四态覆盖和自动倍率，只作为处理问题时的回放工具；
  - 不再要求把整场录像按 1 倍速看完才算“已判读”。
- **移除**：用“全程覆盖率”衡量判读完成度。改为两项：问题清单是否处理完，以及录像和证据缺口是否如实列出。
- **保留文档**：`CONTINUOUS_REVIEW_DESIGN.md` 保留交互与前后台隔离背景；`docs/LIVE_COUNT_REVIEW_PLAN.md` 的外部计数与“疑似额外芯片”等状态定义并入本文第 7 节。

## 13. 已知限制

- **公路密集集团**：自动计数不可靠，依赖集团核对和机位改进。
- **证据不足**：拥挤、遮挡、录像缺口只能如实报告，不能补出证据。
- **号码牌**：逆光和低分辨率时看不清，漏读者的身份要靠名单排除和人工确认。
- **验证范围**：参数来自三场比赛，规模和场地类型有限。
