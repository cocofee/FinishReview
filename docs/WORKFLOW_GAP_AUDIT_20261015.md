# 异常优先流程复查（2026-10-15）

## 当前确认的目标

系统负责从芯片和视频中筛出关键问题，操作员只处理：

1. 疑似一人多芯片、携带成批芯片、无效读数。
2. 密集集团中的人数差异、遮挡与不能可靠对应的局部。
3. 视频有骑手过线但没有芯片，以及妨碍核实的证据缺失。

正常匹配不要求逐人确认照片、号码或过线帧。自动对应不是人工身份确认。
终点线首先是自动视频取样的输入，同时可供人工判读；不能把画线解释成恢复逐人核对。
移除独立“对数”入口不等于取消视频与芯片数量核对。

## 已确认的差异与风险

### 1. 一次携带多个芯片，没有形成一个完整的批次处理流程

`build_video_items` 为每条多余芯片分别创建“两芯片对应一次过线”；
`_bunch_items` 又按芯片时间聚类，达到四条即创建集团，并在文案中把芯片数称为人数。
芯片密集不能证明画面中有一个真实骑手集团。

本次合成输入为一次视频过线、8 条相隔 20 ms 的芯片读数，实际得到：

- 7 条两芯片问题，折叠到 1 条集团问题下。
- 芯片自检另产生 3 条重叠成批读数问题（分别含 6、7、8 条）。

现有删除建议使用单个 `target_bib`，不是批次多选处理。
应把同一异常的证据和相关芯片聚合为一项，区分“疑似携带多芯片”和“真实集团待核”，
逐条保留处理状态，避免确认一个号码就掩盖其余成员。未确认的数量差不得自动删除成绩。

### 2. 芯片自检被视频前置条件阻塞

`ProblemListPanel.live_tick` 在没有终点线配置文件时提前返回，且常规自动启动以正在录像为条件。
芯片自检虽然在 `write_problem_list` 中不依赖视频，但当前自动调度并未独立运行它。
所以“能收到芯片”不保证此时会自动提示成批、重复等读数问题。

应独立调度芯片自检；视频分析等待画线、封存片段或校时不能阻塞芯片异常提示。

### 3. 集团工具仍在，但默认展示没有体现其作用

整团过线图、芯片刻度、原帧点数、附近芯片、号码记录、非选手排除、草稿及补录插值仍在。
集团入口只在选中集团或拥挤项时显示，普通卡片固定为 240×140，不能替代整团核对界面。

应让集团条目直接展示整团范围、芯片数、视频估计数、证据质量及疑点位置，主操作直接进入整团工具。
普通的时间胶卷与沿终点线取样形成的过线图用途不同，两者都要保留，不能互相替代。

### 4. 集团人工计数不是新增加的要求，但还没有实现更细的减负

原实施方案和 Demo 都要求对密集集团逐帧点数，因为并排与遮挡会让自动检测少计；
当前 `completion_issue` 仍要求看完整团并有人工计数。它并不要求给所有正常计数填写号码。

不能宣传成“系统已经可靠找出集团内部所有异常小段，只看小段即可”。
后续应先突出可定位的疑点，再对不能证明安全的剩余范围保留待核，不能以数量相等直接宣告无漏读。
只有差异或身份歧义处需要认号；不能让全部正常运动员回到逐人照片确认流程。

### 5. 现有去重规则有漏报边界，不能承诺找全漏芯片

未配对视频事件只要在任一芯片预期时间 800 ms 内，就会被作为重复变化合并。
本次输入一次正常匹配及其后 500 ms 的额外视频事件（不同取样位置），输出没有问题项，重复计数为 1。
这证明规则会压掉这种输入；不代表该合成事件已经被识别为真实骑手。

规则原意是消除影子和车轮碎片，但也可能合并紧跟的漏读者；不足四条芯片时没有集团项兜底。
应以空间、轨迹或其他独立证据区分重复与另一骑手；证据不足时作为疑点保留，而非静默丢弃。

### 6. 现场画线入口与自动取样输入不一致

底层 `LineGeometry.from_config` 支持斜线；当前视频辅助设置只允许竖直检测线。
应提供真实画面中的终点线几何设置，接到取样、校时、缓存失效与证据版本链路。
仅改按钮名称或放大录像不能修复这一问题。

## 修正优先级与验收

1. 独立运行芯片自检；同批异常聚合并支持明确成员级处理。
2. 接通实际终点线与自动取样；持续录像，只分析已封存短段。
3. 把集团工具作为集团问题的直接主视图，不要求逐人正常确认。
4. 修正漏读合并边界，以真实案例验证误报与漏报，不只验证窗口能打开。

验收必须包含：一人两芯片、一人多芯片、成批携带芯片、正常并排两人、
正常大集团、集团中一人及多人漏读、紧跟漏读、遮挡与无录像、迟到芯片以及上游更正。
分别记录人工处理项数、认号人数、点击数、用时、误报和漏报。
原 Demo 文档记录找到贺兰山 319、550，不等于当前现场系统已经完成同样的端到端验收。
