# 比赛中问题工作台

## 现场流程

1. 设置摄像机、赛事和终点线，开始录像。默认进入“问题清单”，不再要求逐个确认正常通过的运动员。
2. 顶部一行是计数行：“无需人工处理 N 人”加五个类型格——多芯片疑点、集团待核、漏读疑点、记录与圈数、待证据。
   点一格只看该类（再点一次取消），队列和类型入口随之切换；所以“从队列直接处理”不依赖记住隐藏菜单。
   自动通过人数按有效通过事件去重；若其中有人落在仍待核的集团或遮挡时段内，会写成“不代表该时段已核清”，
   这些人的对应不作废，也不需要逐人重新确认。
3. 左侧选择问题，中间回看原录像，右侧处理。当前问题的类型入口就在证据下面：多芯片疑点给“按成员处理批次”，
   集团待核给“打开集团逐帧核对”，漏读疑点给“查看候选证据”（跳到候选原帧）。记录与圈数类不在这些入口里，
   直接用它自己的决定按钮。
4. 底部时间胶卷始终保留整场录像范围。可调整采样、拖动时间、通过“更多”前后翻屏，或点击“跟随最新”。跟随只推进胶卷，不抢走当前问题的原帧。
5. 浏览其他时段会保留当前问题和输入，但锁定当前问题的处理按钮。点击“回到当前问题”，原帧到达后才恢复提交；前后约一秒内可逐帧核对。
6. 需要等待裁判时，填写原因后“暂存”，通过“暂存”筛选恢复。暂存不是已解决。待录像或校时的条目在“待证据”中，没有处理动作。
7. 从胶卷打开可用原帧后可添加“人工问题”。必须填写原因，保存当前视频、机位、帧号和位置；不会直接断言缺少芯片，也不会生成正式成绩。
8. 补录、建议删除和改号改圈进入“待 CycleRace”；导出三张交接 CSV，在计时软件中处理后再明确标记“已在 CycleRace 处理”。可通过“重新处理”撤回本机决定，但不会撤销外部软件的修改。

集团的数量相等只作统计，不能排除漏读与双芯片互相抵消。逐人认号、完整查看录像、处理剩余疑点后才能明确确认完成；
未认号或证据不足时保存进度。旧版集团完成记录保留原始日志和点数，但需按新判据重新核对后才能再次导出补录。

严格配对未通过的过线，即使在芯片预期时刻 0.8 秒内（双方孤立时 1.5 秒内），也只显示候选关联，
同时保留未配对芯片。消息晚到与过线时刻偏差不同，不能用宽时间窗口将疑点自动通过。
同一时刻或相邻帧的变化也可能属于不同选手；规则层只去重完全相同的检测记录，其余保留人工核对。
更新后应重新分析已有赛事，以重新生成候选和分析签名；旧的问题列表不会在读取时重写。

顶部状态栏分开显示 接入 / 录像 / 取样 / 校时 / 分析 和证据缺口；某一项停了或配置改了，显示的是那一项自己的原因，
不是一句笼统的“视频辅助异常”。证据缺口把“还在等证据的条目”和“没有录像可核的芯片数”分开写。

旧的按号码标线、逐人判读保留在“通过记录”。问题工作台屏蔽旧确认快捷键，收到芯片或 CycleRace 焦点消息不切换正在核对的画面。

## 录像与分析并行

- 录像器原来的短段和长归档策略不变：通常约 2 秒封存一个回看短段，约 300 秒封存长归档。受关键帧等因素影响，以播放列表中的实际时长为准。
- 后台采集线程只发布 HLS 播放列表中已经封存的文件，不读取仍在写入的下一段。发布时保留文件并登记稳定原帧 ID。
- 分析使用独立低优先级进程，沿用内存门槛、单线程 OpenCV 和 CPU 繁忙让步机制。每轮结束至少等待 10 秒；没有新录像、芯片或配置变化时不重复启动，不并发积压多个分析进程。
- 线取样只解码新增或变更文件。逐段检测缓存包含相邻短段和参数指纹；末尾加入相邻段后会重新检测边界。配对和校时会按当前数据重新计算，结果通过原子替换发布。
- 实时结果保留约 10 秒证据等待区：使用相邻录像参与配对，但等待区内不下漏读结论。校时尚未成功时明确等待，不能当作“全部正常”。芯片系统若晚于该等待区送达数据，后续分析仍会重新核对；等待区不是网络时延保证。
- 停止录像后补做末轮分析，收尾等待区。手动暂停分析不停止录像。集团逐帧核对期间自动暂停分析，关闭集团窗口后允许继续。
- 已作出的建议单独保存问题快照；后续分析重写问题列表不会把交接建议丢掉。正在查看的问题如果被新分析替代，会保留旧条目和草稿、锁定决定，并提示选择新问题。

## 正式比赛日期与现场测试日期

- 赛事范围由赛事 ID 和赛段 ID 决定，不再把赛事元信息中的日期当作芯片过滤条件；正式比赛日期、芯片原始时间和导出建议中的计时时间保持不变。
- 实时证据定位和后台分析共用日期映射：收到刷卡时，若时分秒与接收时间相符，可用接收日期提出整数天偏移；支持跨年、提前测试、赛后测试及午夜边界。不会把接收时间直接当作过线时间。
- 自动校时先尝试有接收证据支持的日期偏移，再在前后 90 秒范围内精确拟合。配对和反向生成补录建议使用同一模型，避免将测试日期写入正式计时建议。
- 日期映射不是匹配成功的证据。缺少录像、终点线或足够的独立过线样本时继续等待；多个日期的录像同样吻合时明确报告歧义，不自动选择。批量补传或时分秒不吻合的历史记录不能仅凭接收日期强行匹配。
- 在实时模式中切换到尚无赛事数据的保存目录，会保留当前已加载的赛事和通过记录（包括撤销记录），无需等待再次刷卡才能恢复赛事名称；不会覆盖目标目录已有的赛事。

## 接入正在测试的赛事

赛事切换统一从顶部“设置”进入，避免工作台和设置窗口出现两个相互独立的赛事选择器。设置窗口可打开已保存赛事；实时赛事仍由 CycleRace 同步后自动接入。正在录像时需先停止录像再切换。

此前已保存的 `live_received` 状态仍可恢复，显示“完整赛事信息待同步”，不会伪造服务器赛事信息或名单。收到正式赛事信息后，正常按原始版本接续；历史查看与数据文件保持不变。

更换保存根目录时保留已收到的赛事收件箱。收到其他赛事记录时更新计时源接收状态并提示在“设置”中打开对应赛事，或等待 CycleRace 同步；旧缓存不能再仅凭另一条历史通过记录抢回当前页面。

## 文件与资源

- `finish_problems/problem_list.json`：当前分析结果及每机位分析水位。
- `finish_problems/strips/`：线取样和逐段检测缓存。
- `finish_problems/operator_drafts.json`：各问题的输入草稿、暂存原因和人工处理快照。
- `finish_problems/manual_problems.json`：人工发现的问题，独立于分析输出。
- `finish_problems/problem_resolutions.jsonl`：追加式处理日志；`exports/` 为 CycleRace 交接文件。
- `video_timeline.jsonl` 中 `retained_problem_segment` 是问题分析证据，不参与旧的逐人过线窗口自动定位。

为了让建议中的帧引用在长归档生成后仍有效，本版保留分析短段到赛事结束之后，不自动用长归档替换或删除这些文件。**短段和长归档会同时占用磁盘，应按两份录像预留空间。** 长时间比赛仍需观察磁盘余量、分析水位和待分析秒数。

## 验收边界

原型位于 `ui-prototype/live-review-workbench.html`；正式实现为 PyQt 桌面界面，不是嵌入原型网页。

自动化覆盖短段封存、保留与清理、两秒视频分析、尾部等待、检测缓存、长归档去重、草稿恢复、暂停与收尾、问题帧防误提交及旧流程兼容。窗口检查使用离线测试数据。
类型计数行、每类入口、待核时段标记和原型文字一致性另有单元测试；布局只在离屏平台做过几何核对（按钮不越界、自成一行），真实字体与系统缩放下的观感仍待人工走查。

这些验证不替代真实设备联调。正式用于比赛前，应使用现场摄像机和 CycleRace 完成持续录像、芯片延迟/断线重连、密集集团、磁盘压力和长时间积压演练，核对录像连续性与原帧时间。
