## 步骤1：独立芯片自检

### 实现

- 新增 `realtime/live_chip_checks.py`：只读赛事日志，按赛事/赛段重建有效记录，复用已有芯片规则。
  活跃记录采用最新时间、圈次和分组；重复投递不增加有效通过数，历史身份仍供已作废发现追溯。
- `ProblemListPanel.live_tick` 在视频条件判断前触发芯片检查，400 ms合并启动；独立低优先级
  `QProcess` 执行，不在接收线程或界面线程遍历完整日志。暂停视频和打开集团不阻塞芯片检查。
- 子进程仅回传JSON；界面验证赛事和生成代次后，原子发布 `finish_problems/live_chip_checks.json`。
  视频进程继续独占 `problem_list.json`，两者不竞争同一个文件。界面合并结果，保留草稿与当前问题。
- 监听芯片日志、删除标记、赛事范围、元信息变更；失败保留上一版并延迟重试。退出取消定时器并回收进程；
  重启输入签名相同不重复运行，切赛事丢弃旧代次结果。
- 状态栏独立显示芯片结果和视频等待原因；缺少名单、枪时、距离和退赛状态在状态提示中显示。
  显示“已落盘消息/有效通过”，原始读卡数和未经视频分析的候选数保留未知，不填0。
- 修复旧面板将“当前快照缺少目标记录”当作上游删除的问题：只有明确失效记录才证明上游作废。
  此修改不宣称已有完整删除同步能力。

## 步骤3：多芯片批次与成员级最小闭环

### 聚合与安全边界

- 芯片密集窗口合并为有边界的批次，最大跨度1000 ms；不通过连续相邻重叠把整场串成一个批次。

  原发现作为子证据保留，可展开查看，不靠删除候选降低数量。范围更大的遮挡/集团项不强行吞进短批次。
- 只看芯片时显示“密集读数，人数待核”；有视频时分开显示有效芯片记录数和相关视频候选数，不能把记录数称为人数。
  不同机位计数不一致时保留冲突，不取较小值强判多芯片。关联成员不继续计入无需处理的自动通过。
- 批次身份通过前次事件交集延续；迟到成员加入后增加内容版本，不因成员集合哈希变化丢掉操作员草稿。

  `batch_identity_snapshot.json`，在芯片/视频发布者交替或重启后继续延用身份。

## 步骤5：漏芯片发现与处理，避免降噪掩盖漏读

### 规则改动：不再静默丢弃邻近过线

- `problem_rules.py` 删除“只因靠近芯片时间就认定重复”的丢弃分支。靠近已匹配芯片的额外过线不再
  被删除，也不再每个碎片建一条任务，而是按芯片收敛为“附近可能另有过线”疑点（优先级15）。
- 只有能证明是同一趟过线时才合并：同一会话内相隔不超过 `SAME_CROSSING_MS`（150 ms），或同一录像
  文件内相隔不超过 `SAME_CROSSING_FRAMES`（2 帧）；`same_passage()` 只用检测器自身合并过的几何，
  行号与沿线位置不参与身份判断，避免用位置推断人数。合并片段连同间隔和理由写回该选手的
  `merged_fragments` 证据，保留可追溯的合并依据，而不是无声删除。
- 同一芯片附近 300 ms 内的多个碎片合并为一项，但每位成员保留自己的原帧、换算时间、行号和认车
  结论（`evidence.members`）；多位漏读者不共用一帧、不共用一个补录时间。详情说明“可能另有一位
  漏读选手，也可能只是同一人的后轮或影子，请按原帧判断”，判断留给原帧。
- 人数不以芯片为准：无芯片过线条目在前后各2秒内过线达到3处且多于附近芯片时，附 `dense_window`
  证据与“请一并核对”提示；视频侧同一窗口内过线达到3处、至少有1条芯片、过线数多于芯片数且不与
  芯片侧集团窗口重叠时，单独生成 `source="video"` 的小组条目，提示“小组人数不能只按芯片判断，
  请整团点数”。四条芯片不再是漏读保护门槛。
- 处理入口新增“确认是同一次过线”（`same_crossing`）；“非选手/回头/确认同一次过线”必须写明依据，
  界面提示“看不清号码”不能作为排除依据。确认同一次过线只关闭疑点，不虚构骑手，也不产生补录。
- 时间来源显式化：补录清单新增“时间来源”列，区分“校时换算（视频原帧）”“集团内前后过线芯片之间
  插值”“未换算：按原帧人工判断”；集团导出的插值行同时给出前后参考相隔的毫秒数（`bracket_ms`）。

## 步骤6：统一界面，让操作员直接看见三类问题

### 一套类型表，计数行就是过滤器

- `problem_items.py` 新增面向操作员的类型表：多芯片疑点、集团待核、漏读疑点、记录与圈数、待证据、其他疑点。
  24 个 `KIND_*` 每一个都显式归类，测试断言"任何类型都不落到兜底值"；将来新增而忘记归类的类型会落到
  "其他疑点"，仍然出现在计数行里，不会静默消失。
- 方案第6步的计数行是"无需人工处理数量 | 多芯片疑点 | 集团待核 | 漏读疑点 | 待证据"。但一直待在队列里的
  还有发枪前、发枪后过早、圈号重复/倒退、单圈异常、末圈缺读、应到未到、两边记录不一致这些待处理项，
  四列装不下它们。本轮为这些类型补了第五列"记录与圈数"，否则计数行总数会小于队列里的待处理条数，
  操作员会以为队列比计数多。这是对方案布局的一处增列，需接受人确认。
- 类型计数行的每一格都能点：点一次只显示该类，再点一次回到全部；计数行因此既是状态板也是队列过滤器，
  不需要操作员记住隐藏入口。行状态筛选（待处理 / 待证据 / 暂存 / 交接 / 全部）保持不变，改状态会清掉
  类别过滤，类别不会冒充状态。集团成员、批次成员只在父项计一次，不重复计入多个待处理总数。
- 每个问题的主入口按类型给：多芯片疑点走"按成员处理批次"、集团待核走"打开集团逐帧核对"、
  漏读疑点走"查看候选证据"（跳到候选原帧逐帧看这一处变化）。三个入口按钮从面板顶部的工具行移到
  当前问题的证据列，文字取自同一张类型表；同一时刻只出现所属类的那一个。记录与圈数类不套入口，
  直接用它自己的决定按钮（建议删除 / 建议改号改圈 / 已核对）。
- 顶部栏按 赛事 ｜ 接入 ｜ 录像 · 封存到 ｜ 取样 · 校时 ｜ 分析 · 积压 ｜ 证据缺口 分段显示。
  `ProblemListPanel.stage_health` 分五项（接收 / 录制 / 取样 / 校时 / 分析），进度消息按阶段归位，
  录像停止、取样配置变更、校时锚点超差、分析失败各自成句，不再合并成一句"视频辅助异常"。
- 自动对应（`unambiguous_auto_passed`）：按有效通过事件去重，同一次过线出现两条读数只算一人；
  落在待核集团/遮挡时段内的对应保留，但加 `pending_period` 标记并在计数行写明"其中 N 人落在待核
  集团/遮挡时段内，不代表该时段已核清"。拥挤区域里已有独立过线证据的可靠对应继续保留，
  不撤销、不要求逐人重新确认；整段是否核清仍由集团核对决定。标记在每次运行时按当前待核时段重算，
  不会累积成陈旧的旗标。

## 步骤7：真实回放、持续录制与减负验收

范围：离线可做的那部分验收。**设备联调与比赛时长持续负载没有做**，第四场盲测也没有做，
所以步骤7只能记为"离线验收通过、现场验收未完成"，详见本节末。

### 盲回放：按时间释放录像与芯片

- `tools/exception_first_replay.py`：把一场封存工作区或缓存切片复制成工作副本（只读源目录，前后比对摘要，
  `source_untouched` 检查），然后按 `received_at_ms`（芯片修订到达）与 `ended_at_ms`（录像封存）
  逐步改写日志，每一步跑现场同一条 live 管线。芯片修订没到、录像没封存的东西一步都不可见。
- 每一步都做溯源检查：条目的 `event_ids` 必须全在已释放修订里、证据帧所在片段必须已封存
  （`no_future_evidence`）；释放标记覆盖每个封存点、水位单调且落在已释放录像内、最后一步是
  settle 且释放全部输入。三个切片 8/8 项检查全通过，`leaks` 为空。
- 回放同时给出一条事实：**settle 运行（录像停止后）与一次性离线运行的任务集合、摘要完全一致**
  （贺兰山 40 人自动通过 / 27 项待处理 / 112 无法核实；定边307 25/7/240；定边020·023 60/11/226），
  也就是"分步释放不改变结论、算法没有提前看到后来的芯片或录像"。
- 回放抓到一个真实缺陷并已修：录像停止后的 settle 运行把**录像范围之外**的芯片写成
  "等待相邻短段和芯片数据到齐，暂不判定漏读"，等于把"没有录像可核"藏成"再等等"。修法是
  `analyse_camera` 在 `evidence_delay_ms=0` 的 settle 分支持续用录像内的 `no_video` 覆盖结论、
  并把等待数清零；两个切片（020·023 227 处、贺兰山 112 处）在修复后与离线一致，同时补了合成回归
  （录像范围外的读数在 live 下是等待、settle 下是"无录像可核"，且不重复计数）。
- 回放还查出一个显示与清单不一致并已修：批次 id 有两条身份链（分析用自己的旧清单、界面用
  `batch_identity_snapshot.json`），界面首次刷新会给同一批次换一个哈希 id，操作员手里的草稿和
  暂存可能对不上。现在两份身份合并成一个账本（`save_identity`/`identity_chain`），分析与界面都写它、
  都先读它；界面只对账本从没见过的批次采用清单 id。走查里"队列包含每个主问题"因此成立，
  另有两条回归测试锁定（发布者重命名批次时保留操作员手里的 id；账本为空时沿用清单 id）。

### 交互走查（离屏脚本，不是人）

`.field_validation/generated/exception_first/step7_walkthrough.py` 用离屏 Qt 在三个真实切片上走了一遍：
打开面板 → 核对队列与计数行 → 逐个类型点开/再点恢复 → 漏读入口取候选原帧并用 `cv2` 打开该帧确认
可读 → 批次入口是"按成员处理批次"且成员表与清单一致 → 集团入口是"打开集团逐帧核对"且机位与时段正确
→ 写草稿、重启面板、草稿恢复 → 清理痕迹。三个切片全部通过（贺兰山 20 项、定边307 17 项、
定边020·023 20 项，0 失败）；307 切片没有多芯片批次，因此少三项批次检查。
这验证的是控件行为与数据连通，不是操作员的观感、点击手感或现场字体下的排版。

### 赛时是按时间顺序工作，不是按类型批量（来自操作员）

第一轮走查建议"按类型分批"（先做漏读、再做批次、最后集团），这是赛后审计的做法。操作员的实际
流程是从第一位选手过线就开始工作，一条一条按时间往下做，不等整场比赛结束。据此改了界面：

- 队列仍按时间升序，处理一条后该条离开"待处理"，列表自动回到最上面那条未处理项——就是"最老的
  未处理问题"，与时间顺序一致；不引入任何按类型批量的默认动作。
- 新增键盘流（`realtime/problem_panel.py`）：`回车`打开当前行的工具（批次→按成员处理，集团→逐帧
  核对，漏读→候选证据；没有工具就跳到原帧，都没有则提示），数字键 `1–9` 按屏上顺序按下该行的
  处理按钮；方向键沿用表格自身的选择移动。处理完一条后把焦点交回表格，下一行只差一个方向键。
- 键盘只在焦点控件用不到该键时才到达面板（Qt 的传递规则）：号码/原因输入框照常收字符，表格照常
  收方向键。表格会把回车当成自己的"激活"吞掉，因此面板在表格上装了事件过滤器，保证回车在任何
  焦点位置都只触发一次。
- 测试：`tests/realtime/test_problem_panel.py` 新增两项——回车对漏读/批次/集团行分别打开对应工具
  且每次按键只触发一次（表格内与面板上各测一遍）、无工具行跳原帧、无工具无原帧行只提示；数字键
  按屏上顺序按下处理按钮（第 2 键触发"确认是同一次过线"并校验必须写依据，第 1 键触发认号补录并
