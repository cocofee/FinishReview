## 步骤1：独立芯片自检

### 实现

- 新增 `realtime/live_chip_checks.py`：只读赛事日志，按赛事/赛段重建有效记录，复用已有芯片规则。
  活跃记录采用最新时间、圈次和分组；重复投递不增加有效通过数，历史身份仍供已作废发现追溯。
- `ProblemListPanel.live_tick` 在视频条件判断前触发芯片检查，400 ms合并启动；独立低优先级
  `QProcess` 执行，不在接收线程或界面线程遍历完整日志。暂停视频和打开集团不阻塞芯片检查。
- 子进程仅回传JSON；界面验证赛事和生成代次后，原子发布 `finish_problems/live_chip_checks.json`。
  视频进程继续独占 `problem_list.json`，两者不竞争同一个文件。界面合并结果，保留草稿与当前问题。
- 监听芯片日志、删除标记、赛事范围、元信息变更；失败保留上一版并延迟重试。退出取消定时器并回收进程；
  重启输入签名相同不重复运行，切赛事丢弃旧代次结果。
- 状态栏独立显示芯片结果和视频等待原因；缺少名单、枪时、距离和退赛状态在状态提示中显示。
  显示“已落盘消息/有效通过”，原始读卡数和未经视频分析的候选数保留未知，不填0。
- 修复旧面板将“当前快照缺少目标记录”当作上游删除的问题：只有明确失效记录才证明上游作废。
  此修改不宣称已有完整删除同步能力。

  人为同时保留文件大小和修改时间替换模型时，需要手动触发分析才能发现内容变更。

## 步骤3：多芯片批次与成员级最小闭环

### 聚合与安全边界

- 芯片密集窗口合并为有边界的批次，最大跨度1000 ms；不通过连续相邻重叠把整场串成一个批次。
  同一事件的重复投递/修订不累计为多名成员。正常每110 ms一条的集团冲刺不因一秒多读数自动报携带芯片。
- `batch_review.py`把共享事件的密集读数、同一次过线对应多芯片及完全包含在批次内的集团项关联为一个主项。
  原发现作为子证据保留，可展开查看，不靠删除候选降低数量。范围更大的遮挡/集团项不强行吞进短批次。
- 只看芯片时显示“密集读数，人数待核”；有视频时分开显示有效芯片记录数和相关视频候选数，不能把记录数称为人数。
  不同机位计数不一致时保留冲突，不取较小值强判多芯片。关联成员不继续计入无需处理的自动通过。
- 批次身份通过前次事件交集延续；迟到成员加入后增加内容版本，不因成员集合哈希变化丢掉操作员草稿。
  拆分只有一个分支继承原ID，其他分支保存关联；合并保留旧批次关联。界面单独原子保存
  `batch_identity_snapshot.json`，在芯片/视频发布者交替或重启后继续延用身份。

### 成员处理与交接

- 入口：“问题清单 → 选中批次 → 按成员处理批次”。显示号码、芯片、通过时间、事件ID/修订、状态、名单绑定。
  可多选“建议作废 / 确认有效 / 暂存 / 重新处理”，必须填写原因；默认不选任何成员。
  返回主界面查看证据原帧不自动提交尚未保存的勾选。
- 每次多选作为一条持久化事务写入新文件`batch_member_decisions.jsonl`（schema_version=1），
  绑定赛事/赛段、准确事件身份及修订、原帧、校时版本和多机位分析证据；不是覆盖旧整项日志。
  打开窗口后成员发生变化，提交前重新验证；配置或视频证据过期时拒绝沿用旧决定。
- 一部分确认有效、一部分待上游、一部分未处理时，主项显示部分处理。后来加入的成员不继承旧决定；
  暂时缺失的成员保留待证据，不把当前快照里没有该记录当作删除。
- “建议作废”只进入待CycleRace；收到对应事件明确失效后才关闭那个成员。单纯修订号增加、改号改时、
  局部快照缺记录均不证明删除完成。这里的状态判断不承诺上游必定发送删除通知。
- 删除CSV逐条输出所选事件ID、记录编号、修订、成员自己的时间、原因、批次ID、帧及校时版本，附完整证据JSON。
  导出前刷新并核对当前事件状态；已作废或证据过期的成员不再输出。没有自动写CycleRace数据库。
- 旧删除路径不再对不存在或不唯一的号码回退首条记录。原整项日志只读兼容，新批次中的旧整项决定只显示为历史，
  不自动扩散给全部成员；存在成员级批次时也不重复导出旧子项建议。
- 合法双芯片名单绑定用于展示，不能把两块物理芯片等同于两条错误成绩；一个事件的传输修订与两条独立通过记录分开。
  是否上游已合法合并仍需接口语义核实，本轮不自动删除任何成员。
