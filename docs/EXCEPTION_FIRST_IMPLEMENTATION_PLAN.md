## 一、目标与不做的事

### 1. 唯一主线

持续接收芯片、持续录像，系统自动检查三类关键问题：

1. 疑似一人多芯片、携带成批芯片、无效或重复读数。
2. 大集团通过时的视频人数、芯片数量及局部对应异常。
3. 视频发现骑手但芯片漏读，以及影响上述判断的证据不足。

操作员只处理系统筛出的异常，不逐人确认正常运动员的号码、照片或过线帧。
系统输出的是复核结果和更正建议，正式成绩仍由 CycleRace 管理。

### 2. 明确禁止的退化

- 不把每条芯片都变成一条待确认任务，不以“人工确认率100%”为完成指标。
- 不要求所有集团成员都认号；正常对应只需计数或自动对应证据。
- 不因算法少计就自动判一人多芯片，不因人数相等就认定没有漏读。
- 不以隐藏异常、合并掉不确定事件、默认确认等办法降低待处理数量。
- 不把独立“对数”页面的移除理解为取消人数与芯片数量比较。
- 不把画线仅作为人工判读装饰：真实终点线是自动视频取样的输入。
- 不改变比赛日期来迁就现场测试日期，不以日期不一致阻塞接入。
- 不为应用更新或界面调试强制停止正在进行的录像。

### 3. 三类数量必须分开

界面及分析同时区分：原始读卡消息数、去重后的有效通过记录数、视频过线候选数。
重复发送的同一事件修订不能被数成多人；视频候选不是已经确认的人数。
一个运动员合法绑定两个芯片是否已经由上游合并，须通过接口样本和配置核查，
不能直接把“两块物理芯片”等同于“两条错误成绩”。身份映射不明时保留疑点。

### 4. 复用的检测链路与资源边界

```text
已封存录像 -> 沿真实终点线逐帧取样 -> 过线候选
芯片记录   -> 自检/去重/修订         -> 自动校时与时间顺序配对
未匹配候选 -> 本机认车与规则降噪     -> 问题清单/集团核对
```

不引入全帧持续大模型检测，不自动识别每个号码，不实现原方案暂缓的云端大模型。
复用OpenCV DNN认车，只检查需要判别的候选截图；不使用AGPL组件，模型不随安装包分发。
CycleRace计时优先，其次录像、当前回放，再是后台分析。延续独立低优先级进程、
单线程认车、受限解码线程和内存/CPU让步机制；不在比赛中打开CycleRace数据库。
现有1536 MB默认内存门槛已实现，先验证是否适用，不列为从零开发任务。

## 二、最终现场工作流

1. 进入当前赛事，接入 CycleRace；芯片自检立即可用，不依赖摄像机、画线或自动校时。
2. 配置固定机位的实际终点线，开始连续录像；保存完成的短段进入视频分析。
3. 正常可靠匹配进入“无需人工处理”；待视频、待校时与证据缺失明确分开显示。
4. 异常按事件或时段聚合进入队列，一次携带多芯片、一整个集团不拆成几十条默认任务。
5. 点击问题，直接打开该类型的处理工具；先看数量差和疑点，不先挑一个号码逐人确认。
6. 补录或删除建议保存证据、原因和成员范围；交接给 CycleRace，收到对应更正后关闭相关成员。
7. 比赛结束后补做尾段分析，交接剩余待核和证据缺口；不把“没有问题项”冒充全场已核清。

录像不断，分析分批，人工游标独立：正在处理旧问题时，新芯片和新分析结果不抢画面。
录像器继续写下一段；分析器只读已经封存并保留的片段，不等待人工停止录像。

## 三、统一问题与证据契约

### 1. 一项问题应包含什么

| 信息 | 约束 |
| --- | --- |
| 范围 | 赛事、赛段、机位、录制会话、时间区间明确；跨赛事不聚合 |
| 原因 | 多芯片、密集通过、疑似漏读、遮挡等可并存，给出主原因 |
| 数量 | 有效芯片数、视频候选数、人工确认人数分别显示，未知不能填0 |
| 成员 | 每条芯片与每个视频候选有稳定引用，不只存号码文字 |
| 证据 | 原录像、实际解码帧/PTS、机位、线配置版本和校时版本 |
| 质量 | 是否完整覆盖、是否遮挡、是否存在并排或配对歧义 |
| 处理 | 每个成员独立记录建议、理由、待上游/已处理状态 |
| 历史 | 原始发现、后续成员变化、人工操作、上游修订可追溯 |

问题标识不能只用当前成员集合的哈希：迟到一个芯片不应让整件事变成新问题并丢失草稿。
优先保持事件身份，内容变化增加版本；需要拆分/合并时保留关联和旧处理记录。
人工决定绑定当时的成员、修订和证据快照，新加入的成员不得继承旧决定。

### 2. 状态不混用

- 等待分析：录像或计算尚未到达，不下异常结论。
- 待证据：缺画线、校时不足、缺录像等，展示具体原因及范围。
- 待处理：证据已经支持提出疑点，需要操作员决定。
- 部分处理：同一批次部分成员有决定，其余继续保留。
- 待 CycleRace：已生成建议，但正式记录尚未确认改变。
- 已处理：对应更正已验证，或操作员明确确认该问题无须更正。
- 需要重查：上游身份、证据或配置改变，旧决定不再适用。

“自动匹配”“集团数量一致”“人工已核对”不是同义词。
一个成员删除成功不能关闭全批；芯片修订号增加也不等于建议已经被执行。

## 五、逐步实施明细

### 步骤0：固定基线，不再凭感觉修界面

工作内容：

- 记录当前分支、主仓库版本、已有未提交改动；不覆盖用户数据或不属于本步的改动。
- 单独审查此前未提交的竖线快捷入口；不把它当作实际终点线方案发布。
- 定位现有卡片加载测试失败，区分测试路径/环境问题和产品缺图问题，不以跳过测试掩盖。
- 将已复现的8芯片重复问题、500 ms额外过线被合并、无画线挡住芯片检查固定成回归案例。
- 建立真实案例索引：定边双芯片和307漏读、正常并排392/399、同心642漏读、贺兰山319/550集团漏读。
- 真实数据只读，输出到独立验证目录；缺少原始记录的案例明确标为不具备验收条件。
- 核查已有工具和实现版本，先演练现有问题清单与集团工具，记录不能使用的具体环节，不重复开发已可用能力。
- 核查每机位实际生效的线配置、模型路径/文件有效性、取景模式、校时支持数；不能只检查配置文件存在。
- 对照现有接收样本列出CycleRace能力矩阵：补录标记、删除/作废通知、全量记录快照、
  名单及合法芯片绑定、发枪时间、赛段距离、退赛/OTL/DNS。未知不能推断为已有。
- 将上游接口改动另列依赖，不在本项目擅自实现或修改CycleRace；缺依赖的检查显示具体不可用原因。

验收：每个缺口都有输入、当前输出、期望输出；历史已知答案只用于验收，不作为检测输入。
区分“直接调用规则的合成测试”和“从原录像解码的端到端回放”。

### 步骤1：芯片自检不再被录像和画线挡住

主要范围：`problem_panel.py`、`chip_checks.py`、`problem_analysis.py`，必要时新增轻量调度/结果合并模块。

工作内容：

- 收到当前赛事的有效事件变化后，独立触发芯片自检；采用短防抖合并，不阻塞接收线程。
- 检查重复、成批、测试/备用和名单外记录；缺名单就标明无法检查该项，不把全部号码判名单外。
- 芯片结果和视频结果分开计算、统一合并。采用单一发布者或等价串行机制，避免相互覆盖同一JSON。
- 缺终点线、摄像机离线、录像未开始、视频校时不足，只影响视频相关检查。
- 绑定赛事和生成代次，切换赛事后丢弃旧任务结果；退出、重启不重复生成相同任务。
- 显示“芯片自检正常；视频分析等待终点线”等独立状态。

验收案例：

- 不录像、不画线时，重复/成批芯片可以产生疑点；普通单次读数不产生强制人工确认。
- 正常集团冲刺不因1秒内多条读数直接被认定携带芯片。
- 同一事件重复投递、修订、作废、恢复，结果正确且不重复。
- 正式比赛日期与现场测试日期不同仍可自检；不串到历史赛事。
- 芯片结果更新不能清空已有视频问题或人工处理草稿。

完成条件：脱离视频前置条件的自动路径通过测试，并在隔离回放中可见；不是只提供手动命令。

### 步骤2：把实际终点线接入自动分析

主要范围：`finish_line.py`、`line_sampling.py`、`analysis_workspace.py`、设置入口与分析调度。

工作内容：

- 在对应机位的已封存录像帧或受控预览中画实际终点线，支持两点直线及多点折线、节点增删与调整。
- 兼容原有`points`几何和`long_image_lines.json`，可回显定边验收的9点折线；保存不能压成竖线或两点线。
- 归一化坐标按真实画面区域换算，避免黑边、缩放、旋转导致错位；保存前预览采样位置。
- 按赛事、机位和适用录制会话保存线；界面明确当前配置用于哪一个机位。
- 把实际取样线与旧运动检测红黄蓝区域分开命名、存储和使用，不相互覆盖。
- 配置原子保存；取消不落盘，保存失败不留下“内存成功、磁盘失败”的状态。
- 线配置变更记录版本和生效范围，使受影响的取样缓存、校时和问题证据重新验证。
- 摄像机在比赛中移动时不能用新线覆盖整场旧录像；保留旧会话配置，对影响范围重新分析。
- 若启用贴合白线的自动修正，记录实际采用的几何和版本；不能悄悄换取样位置。
- 仅处理封存录像；显示已录到哪里、已分析到哪里、等待原因，录像不中断。
- 提供认车模型路径、每机位取景模式（如`up`、`side-right`、`side-left`）的可见配置与试运行结果。
- 显示模型未配置、加载失败、已启用等状态；未启用时仍保留候选，但提示降噪未启用、待核可能增多。
- 模型内容或取景方式改变时使相关认车缓存失效，不只用同名文件判断模型没变；不影响原始录像。

验收：斜线和9点折线保存重开一致；画面缩放不改变几何；取消无副作用；改线重新分析；
跨段连续、没有线/没有录像/没有校时三种等待明确区分；保存线不重启录像。
使用同一小段候选分别测试模型启用、未配置和加载失败；输出差异可解释，真实漏读不能因降级而消失。

完成条件：在隔离真实录像中，操作员从界面画出的线确实进入取样和问题分析，而非只在截图上显示。

### 步骤3：一人多芯片、携带成批芯片作为一件事处理

主要范围：`chip_checks.py`、`problem_rules.py`、`problem_items.py`、`problem_resolutions.py`、问题面板。

工作内容：

- 将重叠成批窗口合为稳定事件；保留事件成员，设置最大跨度/分割依据，防止链式合并吞掉不同事件。
- 关联同一时间范围的成批芯片、额外芯片与视频证据，只展示一个主问题，子项可展开追溯。
- 只有芯片密集时显示“密集读数，人数待核”；只有视频证据支持才显示“疑似一人多芯片”。
- 不再用芯片数直接写“多少人通过”；真实集团和携带芯片不能仅靠时间密度区分。
- 提供成员列表，可多选建议作废、保留或暂存；展示选中范围和原因，保存成员级决定。
- 迟到芯片进入原批次并重新评估，不复制整件事；新成员保持未处理。
- 导出每个目标事件的准确身份、修订、原因及证据；取消现有按首个事件兜底的模糊批次导出路径。
- 兼容旧单号码处理日志；新日志有版本，旧数据只读兼容，不自动迁移或丢弃。
- 先用现有问题及日志结构实现可验收的批次最小闭环，仅为成员级决定增加必要字段；
  稳定关联、拆分/合并和长期事件管理随测试逐步补齐，不先构建一套通用事件平台。

验收：

- 一次视频过线、8个密集芯片只出现一个主待处理事件，不再有7条默认任务加3条重叠批次。
- 正常并排两人两芯片不能自动删除其中一个；证据不足保留待核。
- 合法双芯片映射、同事件重复消息与两条独立通过记录分别处理。
- 批次确认部分成员后，其余仍待处理；上游只作废一个成员不能关闭整批。
- 多选删除建议逐条准确导出；输入不属于本批次的号码时拒绝提交，不回退到首条记录。

完成条件：可以从“发现一次疑点”走到“批次成员正确交接及关闭”，全过程不要求重复看相同画面。

### 步骤4：接通集团 Demo 的完整作用，而不是恢复逐人确认

主要范围：`bunch_dialog.py`、`bunch_review.py`、集团生成规则和问题入口。

工作内容：

- 选择集团后直接展示整团工具，包含整团过线图、芯片刻度、录像、数量差和质量提示。
- 区分整场时间胶卷（浏览录像）与整团过线图（观察过线分布），不能只留一种。
- 先定位未对应、视频/芯片数量差、并排和遮挡区间；提供上一疑点/下一疑点，显示未查看范围。
- 上述位置先限于已有事件/人工计数能支持的候选，明确“候选定位”而非“已找全漏读”。
  自动分段精确找出每个多余骑手属于后续增强，不阻塞已有集团点数工具交付。
- 保留逐帧点前轮计数、放大、附近芯片、撤销误点、非选手排除、草稿恢复和多机位证据。
- 正常计数不要求填号码；时间刻度仅作对应参考，不冒充身份。
- 若自动证据不足以排除其余区间的问题，仍要求完整团段点数或保留待核；不能只看局部就关闭整团。
- 不改变证据门槛来实现“一键通过”。后续允许局部处理完成，必须有剩余范围可靠性的独立依据。
- 延续原方案对四人以上密集集团的保守核对要求，未有真实证据证明可靠前不能仅以总数一致免核。
  需要完整点数的是被列为待核的集团，不是要求把全场录像逐人确认一遍。
- 集团内多芯片和漏读接入成员级处理；暂时找不到号码可以保留定位标记，不丢进度。
- 打开集团工具只暂停低优先级分析，不停止录像；关闭后恢复调度，不抢原画面。

验收：正常集团、并排、一个漏读、多个漏读、额外芯片、行人混入、严重遮挡、跨录像分段。
复核319和550案例时只用当时的芯片及原录像，不先读后来补录答案。
分别记录“人工点数人数”和“人工认号人数”，证明两者不是同一要求。

完成条件：从问题队列可直接完成原 Demo 的集团操作；正常成员无逐人认号或照片确认门槛。
真实集团减少多少操作和时间留到步骤7实测，不能用合成测试提前宣称。

### 步骤5：补齐漏芯片发现与处理，避免降噪掩盖漏读

主要范围：`problem_rules.py`、过线检测/认车证据、问题处理与补录导出。

工作内容：

- 移除“只因靠近芯片时间就认定重复”的硬决策，保留其作为候选关联条件。
- 结合取样位置、事件范围、相邻帧连续性和可用认车证据判断碎片/影子还是独立过线。
- 证据不足时合并成一项“附近可能另有过线”的疑点，不静默丢弃，也不为每个碎片建一条任务。
- 覆盖单人后紧跟漏读、两三人小组和大集团，不把四条芯片门槛当漏读保护条件。
- 小组人数不能只按芯片推断；没有芯片的视频候选也参与发现密集异常。
- 迟到芯片和尾部等待区先保持待证据；后续匹配关闭对应候选，保留发现历史。
- 处理时只对真正漏读者认号；多位漏读者分别保存证据，不能共用一帧或一个补录时间。
- 时间建议明确来源：可靠校时换算或集团内有效前后参考插值。端点缺参考、次序歧义时不编造精确时间。
- 行人、车辆、回头、推车和阴影可以排除，但证据与理由可追溯；看不清号码不是排除依据。

验收：307、642及集团漏读案例；正常骑手后500 ms真实漏读；正常骑手的影子/后轮碎片；
集团中两个漏读、迟到芯片、首尾缺参考、遮挡和录像缺口。
合成500 ms事件只能验证“不静默丢弃”，是否真实骑手必须用录像确认。

完成条件：已知漏读均进入可追溯的待核或补录流程，误报数量也有记录；不能只以增加告警证明改进。

### 步骤6：统一界面，让操作员直接看见三类问题

主要范围：现有 `ui-prototype/live-review-workbench.html`、`review_window.py`、`problem_panel.py`。

先更新HTML交互原型，再按已验证业务实施PyQt界面；原型不是实际算法完成证明。
原型至少能切换多芯片、集团、漏读、等待证据、部分处理和待交接状态。

布局：

```text
赛事 / 接入 / 录像状态 / 分析进度 / 积压 / 证据缺口
无需人工处理数量 | 多芯片疑点 | 集团待核 | 漏读疑点 | 待证据
------------------------------------------------------------
问题队列          当前类型的证据与工具          当前问题的处理
按事件/集团       多芯片：画面+相关芯片         成员多选与原因
不按每个号码      集团：过线图+刻度+点数        差异/补录/暂存
                  漏读：候选片段+原帧           认号/非选手/待证据
------------------------------------------------------------
整场时间胶卷：录像范围 / 证据缺口 / 问题标记 / 当前回放位置
```

交互约束：

- 主按钮随类型变化，不把同一套小卡片、号码框和删除按钮套给全部问题。
- 一人多芯片集中处理，集团主按钮直接进入整团工具，漏读主按钮进入候选证据。
- 普通通过名单留作查询/抽查，不作为默认任务清单。
- 全场时间胶卷始终可访问；跟随最新录像不能抢走当前问题证据。
- 批次总数按主问题计，相关芯片数另外显示；一个集团不重复计入多个待处理总数。
- 自动对应按有效通过事件去重，并标出其中仍涉及集团/遮挡待核的范围；不能直接等同“无需人工处理”。
- 拥挤区域内已经有独立骑手过线证据的可靠对应继续保留，不能一律撤销，迫使这些选手重新人工确认；
  只对遮挡中的短促变化或其他不可靠对应保留待核。界面清楚区分局部对应与整个集团是否核清。
- 状态故障区分接收、录制、取样、校时和分析，不使用一个笼统的“视频辅助异常”。
- 常用笔记本分辨率及系统缩放下，主按钮不挤出屏幕；集团视图可展开，草稿与滚动位置保留。

完成条件：三类任务均可从队列直接处理，不需要操作员记住隐藏入口；正常选手无需点击确认。

### 步骤7：真实回放、持续录制与减负验收

先离线后现场，不直接在比赛进行中的目录试验新规则。

1. 合成与单元测试：覆盖边界、成员修订、聚合、旧日志兼容、导出和配置失败。
2. 真实录像盲回放：按时间逐步释放录像与当时收到的芯片，不把最终修正名单提前交给算法。
3. 交互走查：实际打开三类问题，核实原帧定位、集团工具、批量建议和重启恢复。
4. 设备联调：连续录像时接芯片、处理问题、改网络连接，观察积压与恢复。
5. 持续负载：覆盖预计比赛时长，记录录制连续性、CPU/内存、磁盘增长、分析延迟分布与最大积压。

三场已用于开发的录像只能算历史回归，不能称为独立盲测。参数和规则冻结后，
另用未参与调参的第四场赛事盲测；没有可用第四场时明确该验证尚未完成。

沿用原验收指标并补充端到端指标：

- 在原三场、相同可用输入和校时口径下，自动校时残差中位数不高于50 ms；
  这是原样本回归门槛，不是任意现场的精度保证。样本不足时不得强行拟合达标。
- 原山地赛目标“顶层视频待处理项/有录像芯片数不超过15%”保留作同口径回归门槛，
  不能通过改分母、隐藏成员或忽略芯片自检达标；另外报告全部主问题数和实际处理用时。
- 历史基线：定边视频26项/298条有录像芯片、自动通过233；同心视频61项/416条，
  加芯片自检后63项。历史口径不等于新方案去重后的数字，变化须逐项解释。
- 认车未启用和启用分别统计，不把无模型运行与历史YOLOX启用结果直接比较；
  原报告中同心无模型约增加83条，说明模型可用性是减负前提之一。
- 芯片接收延迟/丢失必须与不开分析时对照，分析主动让步和最大积压都须记录。

CycleRace交接验收分档：收到已验证的目标更正可以关闭对应成员；缺少删除通知或全量快照时，
不能声称两边完全一致，维持待交接或标记为“人工报告已处理、尚未同步验证”。
既有同一帧/位置第二号码冲突提醒继续保留；每条补录证据独立，不按最近芯片认人。

必须记录的减负指标：

| 指标 | 定义 |
| --- | --- |
| 人工问题数 | 去重后的主事件/集团数量，不是子项或芯片数量 |
| 正常人工确认数 | 目标为0；正常选手不应被强制逐个确认 |
| 人工认号人数 | 只统计需要辨认身份的异常/歧义成员 |
| 人工点数人数 | 集团核对需要的计数，独立于认号统计 |
| 处理成本 | 每类问题点击数、实际操作用时、整场总用时 |
| 检出质量 | 已知异常是否在更正前提示、误报、漏报和待证据范围 |
| 实时性 | 接收与封存后到提示的延迟、分析水位、最大积压 |

硬性放行条件：

- 正常流程不存在逐人照片/号码确认门槛；合成8芯片案例只有一个主事件。
- 可取得证据的已知关键案例均得到正确定位，正常并排案例不被自动删除。
- 所有已知异常逐案报告，不以总体正确率掩盖漏掉319/550等关键问题。
- 未知身份、缺帧、校时不足和遮挡不会被写成正常通过。
- 原录像、原始芯片和已有人工记录保持完整；交接建议可追溯、可撤回本地决定。
- 分析落后或暂停不影响接收和录像；持续负载中的积压、额外短段占盘有明确报告。

不预先承诺“十分钟核完整场”或固定减负百分比。使用同一批录像对比旧操作与新操作，
公开实际耗时、误报和遗漏；未达到减少工作量的目标就继续修正，不能只凭测试通过发布。

## 六、提交、部署与回退

- 每步形成聚焦提交：业务代码、回归测试和步骤记录一起提交，不混入未验收的其他界面改动。
- 提交前检查差异、相关测试和静态检查；规则或持久化变更另跑完整回归。
- 推送功能分支后再按既定主仓库流程合并；日志写明完成的是哪一步及剩余限制。
- 代码合并不等于必须立刻重启现场程序；正在录像时先保留运行，明确部署待维护窗口。
- 需要切换版本时先确认录像已安全结束、短段已封存、进度已保存，再启动新版本测试。
- 配置/日志格式优先向后兼容；改写既有文件前备份，失败可恢复，不删比赛数据。
- 回退通过明确的反向提交或恢复备份进行，不使用破坏性重置覆盖用户工作区。
