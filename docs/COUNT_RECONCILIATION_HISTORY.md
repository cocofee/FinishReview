# 芯片多读、漏读与计数待核

计数服务只接收匿名视频观测与当前实际收到的芯片消息。不能向检测过程输入已知问题的号码、时间或补录结果。已知的 023/020、371/376、307 仅用于回放结束后的验收。

FinishReview 现在保留原始异常和处理历史。数量差出现后，芯片被撤销、移出集团或补入，窗口显示“已处理”，仍能看到原始视频/芯片次数和具体变更。上游报告删除已匹配窗口时，历史窗口仍保留，且不重复计入当前总数。原始接收时间缺失时不会把最终名单伪装成原始状态。

每个时间段在结束后等待 5 秒，再按 `received_at_ms` 还原当时收到的最新 `revision`。迟到消息更新当前名单，但不会抹掉原始差异。没有芯片完整性水位时，这个等待仅用于初步提示，不能证明芯片已收齐。校时、观测或原录像不足时，保持等待或人工待核。

外部服务的观测报告和加上芯片历史后的报告使用不同文件，避免循环读取自己生成的计数。服务依然运行在 FinishReview 之外；本项目没有增加 YOLO、OpenVINO、OCR 或模型权重依赖。

```powershell
.\.venv\Scripts\python.exe -m tools.reconcile_count_history `
  --input D:\count-service\source_observations.json `
  --chip-journal C:\path\race\cyclerace_passage_events.jsonl `
  --output-dir D:\count-service\review `
  --watch
```

`--watch` 每秒检查观测、芯片、人工人数记录是否变化。需要上游计数服务持续提供观测报告；这个命令自身不读取相机、不运行检测模型。处理历史保存到输出目录的 `count_anomaly_history.jsonl`，报告使用临时文件加替换方式发布。

在主界面的“对数”中选择上述输出目录：

1. 选择一个异常窗口。查看收到的芯片名单、原始差异和后续处理历史。
2. “定位录像”优先使用报告中的录像段、原路径、零起算帧号和片内位置，直接打开原帧；录像不匹配时不会跳到别的文件。旧报告仍可按已校时的时间定位。
3. 遮挡或计数不确定时，查看整段后点击“核实人数”。它只修正对账用的视频人数，不写入芯片成绩。记录保存到 `count_reviews.jsonl`。
4. 核片发现无芯片者，沿用“记录漏读号码”保存原帧并进入待补录；补录仍在计时软件中进行。额外芯片也由操作员核实身份后在计时软件中更正。对账数量差不能自动确定应撤销哪个号码。
5. 芯片更正被接收后，名单和历史更新。人工核实绑定到具体视频观测；观测或录像改变后要求重新核片。

只有计数、芯片当前次数相等，并且没有未解决的观测或校时问题，才能显示次数一致。人工核实人数也不能绕过赛事、录像、校时和原帧范围检查。

## 真实录像验收

单机实验数据在 `D:\orca\count-lab`。`scripts/blind_replay.py` 按匿名过线观测与芯片接收顺序回放；校时只用当时已收到的孤立通过，五对观测足够后固定每道线偏移。号码与异常位置不作为输入。完成后才与独立的人工案例清单核对。

在 2026-09-19 的录像中，第一处单人双芯片在 10:29:32.636 提示，另一处遮挡集团在 10:50:30.636 提示，漏读窗口在 11:01:36.636 提示，均早于撤销或补录。遮挡集团只能先提示观测不足，仍需人工核片确认多读者。这是实测的待核提示能力，不能称为自动识别每个错误号码。

实验以至少一道上游线与一道下游线共同支持的最大计数作为计数依据；缺少共同支持时保持待核。即使采用此条件，这组录像仍有额外待核窗口；不能把找到三例当成已证明能找全所有未知漏读，也不能把回放结果当成相机实时端到端运行验收。
