# 终点问题清单：实施记录与真实数据验收

对应 [终点问题清单实施方案](CONTINUOUS_REVIEW_IMPLEMENTATION_PLAN.md) 第 11 节。每一步单独实施、单独验收；本文记录实现范围、默认决定和三场真实数据的结果。

真实数据只读使用：CycleRace 的 `race.db` 先复制到工作目录再读取；比赛目录、录像目录不写入任何文件。验证输出在 `D:\orca\count-lab\out\impl_20261014\`。

## 第 1 步：时间与同步

### 实现

- **时间契约**（`realtime/time_domain.py`）：
  - 芯片时间 `ChipClockMs`：CycleRace 读卡器时钟，唯一正式时间；
  - 录像时间 `RecorderClockMs`：录像段起点 + 实际解码出来的片内位置；
  - 显示时间：芯片域时间按北京时间显示。
  - 偏移只由校时模型换算一次（`ClockModel.to_recorder` / `to_chip`）；证据用 `FrameRef` 固定到原帧（机位、录像段、文件、帧号、片内位置、会话、校时版本），之后不再按时间重新推算。
- **自动粗校、细校和漂移**（`realtime/clock_sync.py`）：
  - 粗校：过线时间减芯片时间，±90 秒、100 ms 分箱，3 箱平滑取峰；同时报告峰值、背景和次峰，峰不明显时提示人工核对。
  - 细校：只用前后 5 秒内没有其他芯片、且预期位置 ±1.5 秒内恰好一次过线的单独过线者；稳健拟合“偏移 = a + b × 时间”，迭代 5 次，保留 |残差| ≤ max(80 ms, 2.5 × 残差中位数)。拟合后按拟合线重新选单独过线者再拟合 2 次，避免长比赛两端超出 ±1.5 秒。
  - 同一机位的多个录像会话共用电脑时钟，共用一条漂移线；某会话的单独过线者整体偏离拟合线超过 100 ms 时只提示，不自动修正。
  - 单独过线者少于 8 人时只估计固定偏移。
- **校时版本**（`ClockModelStore`，`video_clock_models.jsonl`）：每次重新拟合，结果变化超过 5 ms 才生成新版本；旧版本保留，可按版本号读取。
- **人工锚点只做核对**：自动结果与人工校时相差超过 300 ms 时提示核对，不覆盖。主界面“已校准”标签在存在自动校时时显示差值，超过 300 ms 显示“与自动校时差 … ms，请核对”；首人校时仍按原逻辑驱动回放。
- **两边同步检查**（`realtime/sync_check.py`，赛后工具 `tools/cyclerace_sync_check.py`）：
  - 按事件编号末尾的 CycleRace 通过记录编号对齐；
  - 列出：上游有效但未同步、上游已作废本机仍有效、上游已删除本机仍有效、上游恢复本机仍作废、号码或时间不一致。
- 其他工具：`tools/clock_calibration_report.py`（校时报告）、`tools/cyclerace_db_copy.py`（只读取 `race.db` 副本）。

### 默认决定

1. 人工校时只与建立在同一整段录像会话上的锚点比较。建立在短证据片段上的人工校时有各自的片段起点估计，时间基准不同，只列出不比较。
2. 人工确认（逐人确认的原帧）与自动过线的定义不同：操作员标的帧系统性早约 190 ms。报告先扣除中位系统差，再按 300 ms 列出偏差大的确认；这些通常是确认到了别人身上。
3. 同步检查需要 CycleRace 自己的记录，只能赛后对副本运行；比赛中不打开 `race.db`。
4. 本步验收时还没有产品自己的过线检测，过线时间暂用原型脚本的过线结果（`proto_crossings_*.json`，转换脚本在验证目录）。第 3 步用产品的线取样和过线检测重新验收。

### 实时版本需要 CycleRace 提供的数据

赛中不读 `race.db`，所以实时同步检查需要 CycleRace 通过现有事件接口补充：

- 每条通过记录的 `is_manual`（现在只能用“收到时间比过线时间晚 60 秒以上”推断补录）；
- 删除记录时发送一条 `is_active=false` 的新版本，而不是只在本地删除；
- 定期发送记录清单（通过记录编号、版本号、是否有效），FinishReview 据此发现漏收的补录和作废；
- 第 2 步还需要：各组发枪时间、赛段距离、退赛 / OTL 状态（见第 2 步）。

## 第 2 步：芯片自检清单

### 实现

- 清单条目统一为 `ProblemItem`（`realtime/problem_items.py`），芯片自检、视频问题和同步问题共用；每类条目带固定的可选处理。
- 芯片读数按“收到时的样子”重建（`realtime/chip_history.py`）：每条记录取比赛当天第一个有效版本；CycleRace 后来作废或改号的，条目保留并标为“已由 CycleRace 处理”。CycleRace 复用通过记录编号换了号码时，按号码拆成不同读数（贺兰山 3 号记录先后是 903、902、746）。
- 检查项（`realtime/chip_checks.py`）：
  - 测试组、备用组芯片；名单外号码（需要名单）；
  - 同号 10 秒内重复读数，全部为补录时记为“重复补录”；单圈赛同号多次有效通过；
  - 成批读数：200 ms 内 6 条以上，或 1 秒内 3 条以上且含测试、备用、名单外芯片。集团冲刺 1 秒内 5–10 条是正常的（贺兰山最多 10 条），不报；
  - 早于发枪；发枪后过早：早于“赛段距离 ÷ 60 km/h”或“同组前 10% 用时的一半”；
  - 多圈赛：圈号重复、倒退、单圈用时不到组内中位的一半或超过两倍、末圈缺读；
  - 应到未到：名单减已到、减退赛 / OTL / DNS，按组列出，只作参考名单，不计入待处理；
  - 两边同步检查的结果（赛后副本）。
- 赛后工具 `tools/chip_self_check.py`：只用事件接口数据时列出缺少的数据；给出 `--race-db` 时从副本读取发枪时间、距离、退赛状态和名单。`--as-of HH:MM:SS` 按收到时间回放，检查当时就能报出什么。

### 默认决定

1. 补录标记：CycleRace 现在不发送是否补录，收到时间比过线时间晚 60 秒以上视为补录。
2. 过早读数的绝对下限按平均 60 km/h 计算，业余公路赛和山地赛都达不到；可用 `--max-speed-kmh` 调整。
3. 已作废的条目不删除，显示为“已处理”，便于赛后核对和第四场盲测。
4. 应到未到在没有退赛状态时会包含退赛者，报告里注明缺少状态数据。
